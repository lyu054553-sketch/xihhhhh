# 货不压钱｜多任务框并行开发安排

日期：2026-10-04。编写时工作分支为 `lanyangyang`，代码参考 `fa23e91`；各任务开始时以实际目录和当前源码为准，不强制回退到该提交。

> 后续调整：任务 5、6 的决策与执行跟进前端因和现有经营总览／工作台功能重合，已从主应用及源码中移除。下表和对应提示词保留为历史开发记录。

本文件与 7 份提示词用于安排并行开发。本轮没有启动这些任务、创建工作树、修改业务实现或执行应用测试。公共接口由任务框 0 第一阶段产出，当前尚不能当作已存在文件或已实现接口。

## 启动方法

1. 先开启 **任务框 0**，复制 [00 总集成提示词](./parallel-prompts/00-coordination.md) 全文。它先产出公共契约、类型、事务约定和前端 API 适配，再回复“可以启动任务 1—6”。
2. 将该阶段的文件提供给其余任务。如果都在同一项目工作目录中，文件直接可见；若在不同电脑或独立 checkout 中，先同步公共契约和数据包，再启动各模块。
3. 同时开启 **任务框 1—6**，分别复制对应提示词。开发期间遵守文件归属，后端用受控样例隔离依赖，前端按同一响应结构预览。
4. 六个框交付后，回任务框 0 发送下方“开始总集成”的提示词。它负责接线、回归与完整走场。

用户负责管理前端框 5、6，并提供业务口径与材料；队友负责管理后端框 1—4；任务框 0 负责统一接口和最终合并。业务不明确时先记入各自交接记录，避免各框自行给同一规则不同答案。

## 契约最少要定哪些事

- 一份共同的事实上下文：场景、快照、时钟、门店、商品、批次、版本、来源和缺项。
- 统一风险、方案比较、提取草稿、运行事件、确认任务、执行回执及资金结果结构。
- 模块 1—4 的 Python 服务接口及注入方式，避免互相循环依赖。
- 同一数据库的连接、锁和事务边界；表与迁移的负责模块；事件去重和版本冲突处理。
- 前端组件挂载／卸载方式、导航与事项上下文、统一 HTTP 请求方法、正常／缺项／错误响应样例。
- 当前接口继续兼容；新增接口明确计划与实现状态，不能用文档中的假设路径冒充可调用接口。

公共契约路径为 `docs/PARALLEL_CONTRACT.md`，准备完成后由框 0 写入 `ready_for_parallel`。具体请求字段和函数签名由框 0 根据当前实现统一制定，本安排没有提前宣称接口已冻结。

## 先交付哪条流程

第一条共同目标：S01 从事实查询、模型理解、候选计算到一次确认、发货签收、销售到账。S08 用来展示新事实重算，S09 用来展示部分完成和未到账。

基础组件可用后，继续完成 S07 采购＋飞书、S06 促销＋企微、S05 退款＋邮箱。换货／抵款保持已确认的独立计算与状态分支；风险正常／缺项由 S02、S03、S10 覆盖。优先级是接入先后，不能把后面的已确认功能擅自删除。

## 通用业务边界

管理员只确认一次，后端仍保存批准版本和任务；前端显示真实工具事件与结果，不能用固定动画代替分析。三渠道只做本地页面动作并保存，禁止真实发消息。API 总费用不限，仍应有超时、有限重试和工具步数约束。

材料范围为文字和单张清晰截图＋人工确认，PDF 直接解析本轮不做。线上模型不可用时保留输入和历史，提供人工／规则入口；不伪造新的模型调用。

风险允许重叠但金额去重，库存／销售／现金分开记，未来实际回放不提前给 Agent，验收答案不挂进业务工具。现有真实导入数据不得被重置或合成数据覆盖。

执行／核算三状态仍是 D07 建议，开发时先保留旧枚举兼容和完整明细，展示映射集中管理。截图识别、渠道动作或函数已写好均不等于全流程已验收。

## 数据与代码如何共享

每个环境都需有当前源码、公共契约、三份设计文档及 `sample-data/retail-v2/` 整个数据包，包括实际 XLSX。检查工作簿是否已经纳入所用提交；仓库的通用 `.xlsx` 忽略规则仍存在，不能仅凭目录说明就假定文件已同步。

模板 `.env.example` 可以共享；各自 `.env` 不作为任务交接附件。多框在共享目录时不自行切换分支、重置、提交或推送。若使用不同 checkout，交接中写清路径或提交，由集成方统一合并。
