日期：2026-10-03。分支：`lanyangyang`。用户决定先完成不依赖模型的后端任务，模型配置随后提供。

## 本轮完成的行为

1. 共享 SQLite 连接使用可重入锁；写业务在 `BEGIN IMMEDIATE` 事务内完成，审计失败也会一起回滚。不同 Store 连接的版本读取与写入同样受数据库事务保护。
2. 草稿更新／计算／保存、提交、审批、生成任务、重算和回执更新检查明确的版本号。保存同时检查草稿版本和方案版本，冲突不留下半份草稿。相同幂等键不能批准另一版本，失效旧方案不能借重试重新执行。
3. 审批及生成任务时核算共享批次库存、门店商品接收容量和采购行数量。近效期处置合计还为正常预计销售保留库存；旧数据库中已生成任务的占用也计入。修改未执行方案释放旧占用，已生成任务保留占用。
4. 库存 CSV／TSV／XLSX 进入正式快照与明细，参与实际库存金额与老师口径计算；同键冲突、负数、小数数量、未知成本、单位冲突和错误工作表会留下失败批次，不覆盖已有快照。完全相同行去重，规范化文件重复导入不重复库存。其他文件类型仍仅格式校验。
5. 人工确认有证据引用的库存、销量或成本后，事实版本递增，旧未执行方案失效、草稿计算清除。撤回／纠正移除有效案例，并按仍有效确认恢复数值事实；文件原快照始终保留。真实诊断详情同时提供原值、有效值和事实版本。
6. 重算实际调用现有确定性计算器。调拨按当前库存与接收容量缩量；不再单纯复用旧 payload 改版本。不可行时保留 `replan_pending`，事实不会丢失。此能力仍是原动作重新计算，跨动作自动选择尚未完成。
7. 指定版本建议单可以下载，带方案号、版本、快照、计算、状态与来源依据。生成任务仍是待外部执行草稿。回执明确标记人工确认，金额正常存储为数值并保留修改轨迹；已完成任务不允许回退或覆盖最终回执。观察回款不能冒充系统归因收益。
8. 反馈草稿保留原文与日期解释，未接入模型时明确 `manual_required`，不再固定推断未上架。真实今日工作台显示候选核查事项，不虚构负责人、截止时间或可执行订单。
9. 静态服务采用产品文件白名单，数据库、源码、配置和 Git 目录不可经网页读取。健康检查不泄露数据库位置。演示重置默认关闭，启用后也拒绝重置已有真实库存的数据库，并保留其他租户数据。

从仓库根目录使用项目隔离 Python 环境运行：

```bash
# 创建属于本次验证的数据库路径，避免使用原有业务库。
```

## 数据迁移和历史边界

Store 启动采用增量迁移：新增 `inventory_reservations` 表；为旧 `execution_tasks` 补 version（默认 1）；为真实库存明细补 risk_id 关联字段。列检查与 ALTER 在同一数据库写事务内，不重建旧表。旧导入脚本未提供 risk_id 的历史明细继续使用旧行 ID 只读展示；它们不会自动拥有本次新文件的可写核查事实，需按新格式重新导入。

已有版本 payload 不会为了统一字段而覆写。本轮新计算与新保存的金额以 JSON number 表达，未知值保持 null；SQLite 成本真值仍使用十进制文本，HTTP 响应做统一数值转换。历史版本导出保留原始内容。

真实详情允许有证据的人工覆盖事实；库存总览和候选选取仍表示文件快照时点。需要更新总览时重新导入文件。只上传库存不足以推算订单减量、效期处置、调拨路线或未来现金；这些入口明确阻断缺项。

## 交给朱的具体改动

1. 读取草稿和方案各自版本；draft／calculate 使用草稿版本，save 额外使用方案版本，submit／approve／execute／replan 使用方案版本，status 使用任务版本。
2. 首次创建草稿版本为 0；首次创建方案为 0，但演示风险 1 本来已有 V1 方案，不能把它当成没有方案。
3. 成功后刷新并保存响应版本；409 保留编辑内容，展示冲突，再加载新版供用户核对。不能自动按新版本重发审批。
4. 接口失败包括 HTTP 400／409／422 和导入批次 status=failed。validated_only 不能展示为数据已进入业务计算。
5. 更新库存模板为第 8 节冻结字段；按单位展示，缺项不补零；添加版本建议单下载和明确人工确认入口。
6. 按并发、旧版本拒绝、导入数据改变计算、确认→重算→重新审批、回执金额及失败恢复完成浏览器验收。
