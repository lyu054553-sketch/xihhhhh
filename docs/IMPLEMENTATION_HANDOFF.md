依据：[比赛版设计草案 v0.8](./HACKATHON_SYSTEM_DESIGN_DRAFT.md)、[当前 API 契约 v1.4](../API_CONTRACT.md)。

本文把已确认需求拆成开发任务。职责安排依据产品负责人擅长业务与前端、队友擅长后端；交付顺序和具体任务分配是本轮建议。当前状态来自源码阅读，不是已通过应用测试的结论。本轮仅整理文档，未运行测试。

多任务框并行开发时，使用 [并行开发安排与 7 份可复制提示词](./PARALLEL_DEVELOPMENT.md)。它进一步限定文件归属，并安排公共契约先行、六个模块并行及最后总集成。

## 1. 还需要产品负责人决定或补充什么

| 类型 | 剩余事项 | 建议或所需信息 |
|---|---|---|
| 产品确认 D07 | 执行与核算状态 | 执行：待执行／执行中／已完成；核算：待核算／核算中／已核算。部分进度显示数量／金额，异常显示“需处理”，取消留历史 |
| 产品确认 | 第 11 节验收清单 | 建议整体采用：当次真实提取、输入变化重算、一次确认、刷新恢复、部分执行与到账分开、金额可追溯、断网降级 |
| 执行信息 D06 | 今晚具体截止时间 | 整个作品今晚交付已经明确；补充可用版本截止时刻，便于安排联调与讲解准备 |
| 接入条件 D02 | 实际可用的 API 配置 | 三家入口和总费用不限已确认；至少配置一条可用的文本与图片调用路径，可由同一家服务提供。模型具体选型和参数可交给后端，密钥在各自本地配置 |

不必重新确认：五大能力范围、数据规模、一次确认流程、三渠道本地模拟、单张截图＋人工确认、暂缓 PDF、API 总费用不限。上述剩余项不影响先进行数据接入、页面组件和接口草案工作。

## 2. 当前能复用什么

| 现状 | 复用方式 |
|---|---|
| 现有清新绿前端与五个业务入口 | 增量补齐材料确认、方案比较和执行结果，不整体重写页面 |
| 库存 CSV／TSV／XLSX 正式入库 | 保留现有库存入口；销售、订单、效期等其他新表补充接入能力 |
| 调拨、临期、采购的计算与重算基础 | 核对当前公式，用统一事实驱动，补齐多方式比较及业务约束 |
| 方案版本、审批、执行任务与人工回执 | 复用现有记录；将管理员确认与任务创建衔接成一次操作，补齐执行和核算状态 |
| 7 个本地 XLSX 数据文件 | 开发统一加载器与场景隔离；生成文件不等于应用已经读取 |
| DeepSeek／千问／MiniMax 后端配置 | 已有 `.env.example`、`backend/model_config.py` 及启动读取；尚无真实模型请求和截图提取 |

源码仍有 `manual_required` 的反馈提取、其他表 `validated_only` 的导入状态；现有审批和生成执行任务仍是两个操作。真实 AI 编排、三渠道完整本地流程、销售与到账核算尚需开发。

## 3. 职责分配

### 产品负责人：业务与前端

- 写清每个场景的业务目标、输入、限制、预期动作和反例；确认金额代表什么。
- 设计风险证据、方案对比、材料确认、执行跟进与结果页面；保持现有清新绿风格。
- 制作采购截图、退供条款、供应商回复与业务回执等代表材料，核对商品、单位、日期和金额与 XLSX 一致。
- 根据共同约定的响应样例开发页面，集中使用前端 API 适配层；展示后台返回的计算与状态。
- 负责飞书任务卡、企微促销预览、邮箱草稿及回复的本地页面交互。
- 准备比赛讲解、录屏与页面操作路线；从业务角度检查结果是否能讲清货与钱的变化。

### 队友：后端与 Agent

- 定义新数据表、加载器、场景快照及时间过滤；接入现有导入服务。
- 实现风险规则、候选比较、数量与效期约束、促销和退供计算及资金核算。
- 接通模型请求、图文提取、结构化输出、受控工具调用、反馈重算、超时与失败处理。
- 保存方案版本、审批、执行任务、渠道动作、回执、库存和资金事件；处理重复操作与冲突。
- 提供前端需要的接口、响应样例和结构化错误；实际实现后更新当前接口契约。
- 负责计算与状态一致性的开发验收、启动依赖与运行日志；与产品负责人一起进行页面联调。

业务规则由产品负责人说明和确认，公式与库存／资金变更由后端实现。前端可以格式化金额、校验必填项和显示预览，最终数量、金额及完成状态以接口返回为准。

## 5. 今晚怎么同时推进

### 第一批：接口约定与并行准备

1. 共同确定 T01 的响应样例和已有接口复用方式。
2. 队友先推进 T02，并接通 T03 的模型请求基础。
3. 产品负责人同时用这些响应样例制作材料确认、方案对比、执行跟进与资金结果组件，准备代表材料。

### 第二批：完整调拨主线

联通 T03—T06：输入目标 → 查询证据 → 比较 → 一次确认 → 发货／签收 → 销售／到账。确认闭店或运费变化时，重新计算并展示版本变化。S09 用于检查部分执行和部分到账的呈现。

### 第三批：接入其他已确认场景

复用同一材料提取、比较、确认、任务及结果组件完成 T07—T09；T10 随业务事件同步。促销、采购各一条代表流程，退款走完整回放，换货／抵款维持已确认的独立计算与状态分支。

### 第四批：联合走场

按 T11 完成页面操作、刷新、模型不可用和金额核对；再整理讲解材料。今晚具体时间未给出，因此这里给依赖次序，不承诺未经评估的小时数。队友报告不能按时完成的项时，由产品负责人明确范围取舍，不能用固定成功动画替代真实调用。

## 6. 每个功能如何交接

产品负责人提供一页场景卡：

1. 用户想完成什么、从哪个页面进入。
2. 选择哪家店、哪个商品／批次、使用哪些材料。
3. 有哪些约束、哪个动作需人工确认。
4. 成功、缺数据、失败、部分完成时分别显示什么。
5. 哪些结果必须由程序计算，如何判断业务结果合理。

队友返回一份接口包：

1. 方法与路径，标记计划／已实现／已联调。
2. 请求、正常响应、缺数据响应和失败响应样例。
3. 商品单位、金额口径、关联 ID、方案与任务版本、日期时区。
4. 哪些状态转换合法、重复操作如何处理、刷新读取哪个接口。
5. 本功能已有的验收结果及已知缺项。

前端开发 Mock 应复用同一响应结构，集中放置；联调时切换到实际接口。接口调用失败展示失败及保留输入，不静默切换成 Mock 成功结果。

交给队友的资料包括：本任务表、比赛版设计草案、演示数据需求、当前 API 契约、`sample-data/retail-v2/` 整个数据包，以及不含密钥的 `.env.example`。

**数据包交接注意：仓库当前忽略 `.xlsx`，普通 Git 推送不会带上这 7 个工作簿。** 本次应单独交付这份数据目录中的工作簿和 manifest；或在双方确定后仅把这 7 份合成样例明确加入版本管理。各自的 `.env` 不作为交接附件。

建议分别使用前端和后端工作分支，约定上述文件归属。共同文件由主责方整合；新增接口先交响应样例，合并后立刻联调对应流程。无需等全部后端做完才开始前端，也不要等所有页面做好才首次联调。
