## 1. 要交付什么

生成一套相互关联、可复现的零食连锁样例，使同一批商品能够完整走过：

**库存与销售事实 → 分别识别滞销、临期 → 核查原因 → 比较处置方式 → 确认方案 → 执行回执 → 销售与结算 → 复盘资金效果。**

数据必须回答：

1. 哪家店、哪个商品、哪一批货，为什么需要关注？
2. 留在原店、调拨、促销、退供分别会怎样？哪些方案做不了，为什么？
3. 有多少货可以分配给每种方案？是否会重复处置同一批货？
4. 谁确认、谁执行，实际完成多少？
5. 钱什么时候进出账户？哪些只是预计结果或应付账款变化？

### 1.1 已确认首版规模

| 项目 | 要求 |
|---|---|
| 企业 | 1 家虚拟企业“零食仓”，所有数据标记为演示 |
| 门店 | 50 家统一主数据；其中 6 家承载完整主线场景 |
| 主线门店 | 西湖古荡店、西湖文三店、余杭未来店、上城庆春店、拱墅运河店、滨江长河店；优先沿用现有门店 ID |
| 商品 | 至少 12 个 SKU，覆盖坚果、膨化食品、饼干糕点、果脯糖果、饮料；使用明确规格与单位 |
| 批次 | 每个有库存的门店商品至少 1 批；主线商品至少 2 个不同效期批次 |
| 历史 | 2026-07-05 至 2026-10-02，90 天逐日数据 |
| 决策时点 | 2026-10-03 09:30，库存快照截至当日 00:00；样例明确此前没有未同步的当日交易 |
| 后续回放 | 2026-10-03 至 2026-11-01，30 天分阶段揭示的执行、销售、结算事件 |
| 场景 | 第 10 节的代表场景；案例库每类展示 1—2 个即可 |
| 随机性 | 固定种子 `20261003`；主线场景固定设计，背景数据才使用受约束随机生成 |

90 天是首版演示规模约定，不代表足以训练可靠的价格预测模型。

50 家店若都展示在经营汇总中，就都要有可核对的基础库存、销售和资金口径。完整调拨比较首版可限定上述 6 家店；其他门店缺少运输或需求数据时，应显示“不在本次可评估范围”，不能编造推荐分数。若实际只生成 6 家基础数据，页面应显示“已接入 6 / 50 家”，汇总也只能统计这 6 家。

## 3. 所有数据必须遵守的口径

### 3.1 字段、主键与类型

- ID 使用字符串。枚举使用英文稳定值，另有中文显示名；不得依赖门店名称或商品名称做关联。
- 日期使用 `YYYY-MM-DD`，时间使用带 `+08:00` 的 ISO 8601。
- 金额单位为人民币元，与现行 API 一致；最多两位小数，计算过程使用 Decimal。百分比按 0—100 表示。
- 包装零食的基础单位数量为整数。箱、盒、袋的换算必须有明确转换系数；不同规格使用不同 SKU。
- 数量、天数为整数，小时与距离可带小数，金额与比率使用十进制数，标志使用布尔值；带 `[]` 的字段为数组。各文件须在字段字典中逐一列出类型、必填条件和枚举。
- 未知值使用 `null` 并给出缺失原因。`0` 表示已知为零；CSV 空单元格在加载时按字段定义转换为 `null`。
- 本演示使用统一的未税价格和成本口径，暂不模拟税额。真实接入必须另外定义税额与结算口径，不能混用含税售价和未税成本计算毛利。
- 所有事实记录携带 `tenant_id`、`record_id`、`source`、`is_demo`、`occurred_at`、`known_at`。快照记录另有 `snapshot_id`、`as_of_at`。
- `occurred_at` 是事情发生时间，`known_at` 是系统获知时间。迟到反馈只能从获知时点起影响新决策。
- 决策输入关联 `data_version`、`policy_version`；每次方案另有 `proposal_id`、`proposal_version`。

### 3.2 批次与金额去重

- `lot_id` 表示可追溯的商品生产／采购批次；供应商原始批号用 `supplier_batch_no`。转店后保留 `lot_id`，若当地重新编号需保留 `origin_lot_id`。
- 库存行唯一键：`snapshot_id + store_id + sku_id + lot_id + stock_state`。
- `stock_state` 至少区分 `on_hand`、`in_transit`。冻结、损坏、预留数量单列，不能作为可调拨库存。
- 已发货未收货数量放在在途位置，全企业库存统计不能同时算作调出店现货、在途和调入店现货。
- 待关注库存成本按风险命中的实际库存行取并集后计算。同一行同时滞销、临期，金额只计一次。
- 首版采用“被风险标记的库存成本”口径。预计卖不完的数量与成本单独展示，不能与整批风险成本混用。
- 同一个销售、退款、运费或采购付款事件只能入账一次。不同 Agent、不同案例引用同一事件时不能重复加总。

### 3.3 现金、成本和收益

| 名称 | 定义 |
|---|---|
| 库存占用成本 | 企业拥有的库存数量 × 对应单位成本，按明确的在库／在途范围统计 |
| 销售收入 | 已发生销售，扣退货与折扣后的收入；可能尚未结算到账 |
| 销售回款 | 有收款或结算流水支持的实际到账 |
| 预计回款 | 根据销量、售价和结算日期预测的未来到账 |
| 少付采购款 | 相对已冻结的原采购计划，在相同周期内减少的现金流出 |
| 延期付款 | 把现金流出移到后期；不是永久节省采购成本 |
| 抵扣应付 | 信用单应用于指定应付单据，使之后少付款；不是现金退款 |
| 商品毛利 | 销售收入 − 已售商品成本 |
| 扣执行费用贡献 | 商品毛利 − 明确关联的运费、促销费等；未含房租人工等时不能叫净利润 |
| 增量收益／现金改善 | 方案与基线的同周期差额；基线为估计时必须标记“估算”，不能当成已证明的因果效果 |

库存减少可能来自销售、退供、损耗等不同原因。调拨在企业内部移动库存，调拨完成时企业总库存成本不会因此下降，也不会因此增加账户余额。

## 4. 分别识别滞销与临期：最小数据需求

### 4.1 必需字段

| 数据对象 | 粒度／主键 | 必需字段及含义 |
|---|---|---|
| 门店 `stores.csv` | 每门店 | `store_id`、`store_name`、`region`、`store_type`、`latitude`、`longitude`、`coordinate_system`、`open_date`、`status` |
| 商品 `products.csv` | 每 SKU | `sku_id`、`product_name`、`category_id`、`specification`、`base_unit`、`purchase_unit`、`units_per_purchase_unit`、`shelf_life_days`、`storage_condition` |
| 商品批次 `lots.csv` | 每 SKU 批次 | `lot_id`、`sku_id`、`supplier_id`、`supplier_batch_no`、`production_date`、`expiry_date`、`purchase_order_line_id` |
| 库存快照 `inventory.csv` | 门店 × SKU × 批次 × 库存状态 | `inventory_id`、`store_id`、`sku_id`、`lot_id`、`stock_state`、`quantity`、`shipment_line_id`、`blocked_qty`、`reserved_qty`、`unit_cost`、`sellable_until`、`snapshot_id` |
| 日销售 `sales_daily.csv` | 日期 × 门店 × SKU × 价格／活动 | `sales_day_id`、`date`、`store_id`、`sku_id`、`sold_qty`、`customer_return_qty`、`sales_amount`、`refund_amount`、`sold_cost`、`returned_cost`、`regular_unit_price`、`actual_unit_price`、`promotion_id` |
| 可售状态 `availability_daily.csv` | 日期 × 门店 × SKU | `date`、`store_id`、`sku_id`、`opening_qty`、`closing_qty`、`open_hours`、`on_shelf_hours`、`in_stock_hours`、`listing_status`、`stockout_flag` |
| 风险规则 `inventory_policies.json` | 门店／品类／SKU 有效规则 | `policy_id`、`scope`、`valid_from`、`valid_to`、`slow_coverage_days_threshold`、`min_observed_days`、`expiry_alert_days`、`stop_sale_days_before_expiry`、`safety_stock_qty`、`target_coverage_days`、`rule_version` |

补充约定：

- `sellable_until` 为首个不可销售日期，由商品效期和企业停售政策推导并记录依据；不同门店政策不同时允许不同停售日。销售日期必须早于该日期。
- `quantity` 是该库存状态下的实物数量；在库记录适配现有 API 的 `on_hand_qty`。在途记录必须关联 `shipment_line_id`，不得计入门店当前可售量。
- `sold_qty`、`sales_amount`、`sold_cost` 均为未扣顾客退货的销售数据，其中销售额已经扣成交折扣；净数量、净收入、净销售成本分别扣对应退货数量、退款金额和退回成本。财务退款与可再次销售的实物退货分别记录。
- `reserved_qty` 必须可追溯到有效的方案预留明细，不能是随意填入的数。
- 日销售有多种价格时拆行；可售状态只保留一条门店商品日记录，不能因价格拆行重复累计营业小时。
- 如无法拿到批次销售，可以先保留 SKU 级销量，并将“先到期先出”等批次分配方式标为假设，不能称为真实批次售出记录。
- 零销售必须有日记录，区分“营业、有货但没卖出”“缺货”“未上架”“闭店”“缺数据”。
- 上述表还要生成对应库存变动明细，保证期初、进货、销售、退货、调拨与期末相互对得上，字段见第 8 节。

### 4.2 首版识别规则

以下阈值为演示配置示例，不是零售行业通用标准。

1. **滞销判断**：有足够正常营业且有货上架的观察数据时，计算库存覆盖天数，并与对应规则阈值比较。首版可设覆盖天数大于 60 天进入滞销候选。
2. **临期判断**：批次剩余可售天数大于 0 且不超过预警天数。首版可设预警阈值 21 天；剩余可售天数小于等于 0 时进入不可销售处置状态。
3. 两种判断分别运行，允许同时命中。不得在判断完“滞销”后跳过临期检查。
4. 临期不等于一定卖不完。另行预测停售前剩余数量，再决定是否需要干预。
5. 无有效销量、缺货或未上架时，返回“待核查”及证据缺项。零销量不能显示“覆盖 0 天”，也不能仅凭零销量断言无人购买。

简单演示公式：

```text
日均销量 = 观察期净销售数量 / 有效可售天数
库存覆盖天数 = 当前可售库存 / 日均销量
剩余可售天数 = sellable_until - 评估日期
```

有效可售天数不足或销售为零时，覆盖天数保留空值及原因。调整缺货、闭店等影响后应保存计算方法版本；历史原始销量不能被覆盖。

滞销初步在“门店 × SKU”判断，再关联其批次；临期直接在“门店 × SKU × 批次”判断。对多个批次预测滞留数量时按明确的批次销售顺序分配需求，不得让同一笔需求同时消耗两个批次。

### 4.3 至少包含四种基本样例

下表假设 30 天均正常可售，使用上面的 60／21 天演示阈值。每行对应一个独立样例，单位按该 SKU 规定。

| 场景 | 商品示例 | 当前库存 | 近 30 天销量 | 覆盖天数 | 剩余可售天数 | 预期风险 |
|---|---|---:|---:|---:|---:|---|
| A | 每日坚果礼盒 750g | 100 | 30 | 100 | 10 | 滞销、临期重叠 |
| B | 炭烤腰果礼盒 600g | 90 | 30 | 90 | 120 | 仅滞销 |
| C | 海盐薯片分享装 80g×8 | 60 | 300 | 6 | 10 | 仅临期，正常销售可能清完 |
| D | 酸奶夹心饼干 100g | 60 | 180 | 10 | 120 | 两种风险均不命中 |

另加一个“上架不足导致销量低”的核查分支和一个“缺销量数据”的分支，避免系统机械触发促销。

### 4.4 派生输出，不作为原始答案喂给 Agent

`risk_assessments` 保存：`risk_id`、`store_id`、`sku_id`、`lot_id`、`risk_tags[]`、`evidence_ids[]`、`coverage_days`、`remaining_sellable_days`、`predicted_unsold_qty`、`risk_inventory_cost`、`missing_fields[]`、`calculation_version`。

`risk_tags` 描述风险；`recommended_action` 描述计算后的建议。两者必须独立，同一个风险可以比较多种行动。现有 `risk_type` 部分承担行动分类用途，需通过兼容适配改造，不能把新规则直接塞进旧枚举。

## 5. “比较四种处置方式”和“候选门店是演示参数”是什么意思

### 5.1 当前限制

当前候选网络包含预先配置的库存、日销量、安全量、距离、运费和评分权重，用于计算和地图演示。这些数值没有完整来自“当前选中商品在每家店的同一时点业务事实”。换一个商品，候选店也可能沿用同一组参数。

因此，地图有 50 家店、能够生成调拨数量，不等于系统已经基于 50 家店的逐商品需求，找到了更合适的方案。

允许使用合成数据。需要改进的是：**用可解释、可关联、可复算的数据支撑建议。**

### 5.2 调拨还需要的数据

| 数据集 | 必需字段 |
|---|---|
| 门店商品配置 `store_products.csv` | `store_id`、`sku_id`、`is_listed`、`can_receive_transfer`、`capacity_qty`、`safety_stock_qty`、`target_coverage_days`、`min_receive_sellable_days` |
| 逐日需求 `demand_forecasts.csv` | `forecast_id`、`store_id`、`sku_id`、`date`、`demand_low`、`demand_base`、`demand_high`、`method`、`assumption_id`、`generated_at`、`data_version` |
| 运输线路 `transfer_routes.csv` | `route_id`、`from_store_id`、`to_store_id`、`distance_km`、`dispatch_calendar`、`travel_hours`、`handling_hours`、`fixed_fee`、`fee_per_unit`、`max_qty_per_trip`、`storage_condition`、`valid_from`、`valid_to` |
| 预计到货 `inbound_shipments.csv` | `shipment_line_id`、`purchase_order_line_id` 或 `transfer_order_line_id`、`store_id`、`sku_id`、`lot_id`、`shipped_qty`、`received_qty`、`expected_arrival_at`、`status` |
| 门店日历 `store_calendar.csv` | `store_id`、`date`、`is_open`、`can_receive`、`receive_window`、`capacity_override`、`known_at` |

接收量应通过逐日模拟核算：接收店已有库存、已确认在途、同一商品其他批次都要先纳入供给，并扣除同期需求。不能直接用“日销量 × 剩余天数”作为这批调拨货能卖出的数量。

示例：某店日销 8 袋，但已有 200 袋、还有 100 袋即将到货，它未必适合继续接货。另一家日销 5 袋、现货只有 5 袋、没有在途，可能更合适；仍需检查效期、到货时间、安全库存、容量和运费。

### 5.3 四种方式如何公平比较

每次比较冻结同一商品批次、决策时点、数据版本、评估截止日和经营目标。目标例如“未来 14 天净现金流入尽可能多，同时满足最低毛利与缺货限制”。目标和权重由规则或用户明确，不能由模型随意决定。

| 方式 | 需要计算 |
|---|---|
| 保留原店 | 正常售价下预计售出、剩余、到期处置及现金到账时间 |
| 跨店调拨 | 原店和接收店销售变化、在途时间、运费、容量、安全库存、剩余风险 |
| 原店促销 | 调整后价格、需求假设、销售结构变化、活动费用、剩余风险 |
| 退供 | 条款是否允许、供应商是否确认、可退数量、净结算金额、结算方式和日期 |
| 组合方案 | 上述方式分配不同数量后的总结果，检查共享库存及需求冲突 |

统一输出字段：`strategy_id`、`feasibility`（`feasible/blocked/needs_confirmation`）、`blocking_reasons[]`、`assumptions[]`、`allocated_qty`、`expected_sold_qty`、`expected_unsold_qty`、`expected_cash_in`、`expected_cash_out`、`expected_net_cash`、`expected_gross_profit`、`execution_cost`、`incremental_net_cash_vs_baseline`、`settlement_timeline[]`、`confidence_basis`。

供应商未确认时，退供只能作为“待确认的条件方案”。同一促销需求假设下，不能把正常销量与促销后的总销量再次相加。不可行方案要保留原因，而不是从比较结果中消失。计算器只应宣称“当前候选方案中的推荐”，除非确实完成了所声明范围的优化求解。

### 5.4 总部统一决策：门店反馈异常，老板决定是否改方案

**用户已确认。** 首版按老板／总部有调拨决策权设计，不将“接收店愿不愿意收货”作为额外审批环节。

```text
系统推荐或老板指定 A 店 → B 店
  → 校验数量、效期、容量及运输条件
  → 老板确认调拨
  → A 店出库、B 店验收
  → 出现客观异常时上报
  → 系统重算可选处理方案，由老板确认变更
```

- B 店不能因为主观不愿意执行就自行否决已经批准的调拨。
- 门店可以上报实物数量不符、货损、存储条件不满足或已知库存与系统不一致等事实；涉及无法执行或不能正常验收时，记录“执行异常／待总部处理”，不能虚填完成。
- 老板指定 B 店时，系统将目的地作为明确约束。发现问题后解释原因并给出修改建议，不擅自改成 C 店。
- 需求变化足以影响方案结果时触发复算；需求有日常小幅波动不必每次都打断执行。
- 审批后的数量、目的地、价格等实质变更需要老板再次确认。已完成的出入库不能通过重算撤销，只能基于剩余数量提出后续动作。
- 比赛只采用管理员代表老板发起：“确认方案并安排执行 → 跟进”，后台保存审批和任务；不重复自审批。员工提交与真实权限流程留待后续。

原表述“接收门店拒收或需求变化时重新规划”统一改为：**“执行条件或需求发生重要变化时，系统提出调整建议，由老板确认后执行。”**

新增 `execution_exceptions.json`：`exception_id`、`task_id`、`reported_by`、`exception_type`、`affected_qty`、`evidence_ref`、`reported_at`、`status`、`headquarters_decision`、`resolved_by`、`resolved_at`、`replacement_proposal_id`。

### 5.5 黑客松版：演示录入路线与运费

**用户已确认黑客松采用“演示录入路线”。** 比赛前以 CSV／配置文件预置线路，页面读取这些记录展示和计算；可由演示人员修改后重新计算。实时地图算路、实时承运报价和运输系统接口留到后续试点。

每条演示线路至少录入：

| 字段 | 含义 |
|---|---|
| `route_id` | 线路编号，关联调拨方案 |
| `from_store_id`、`to_store_id` | 调出、调入门店；使用统一门店主数据 |
| `route_label`、`route_points` | 路线名称和地图示意点列；示意线路不宣称为实时导航路径 |
| `distance_km`、`travel_minutes` | 录入的估计距离和行驶时间 |
| `dispatch_rule`、`handling_minutes`、`eta_days` | 发车、装卸与预计到货约定；与行驶时间一致，不把十几分钟行驶时间直接当成整个到货周期 |
| `fee_amount`、`fee_basis` | 运费金额与计价口径；演示主线可用每趟固定费用 |
| `max_qty_per_trip`、`quantity_unit` | 该费用和运输容量适用的数量及单位；不适用混合商品时明确限制 |
| `valid_from`、`valid_to` | 参数有效范围 |
| `source`、`is_demo`、`version` | 固定标明人工录入演示来源、演示标记及版本 |

建议以一个调出店、至少三个候选接收店形成对比，配置不同运输费用和到货条件。门店的需求、现货、在途仍从同 SKU 的统一样例读取，不放在线路表里写死推荐结果。

页面统一显示 **“演示路线 · 运费为录入估算”**。调拨主线的 24 元运费来自对应线路记录；地图、方案、现金计算和案例全部引用这一记录。修改运费、到货时间后必须触发计算，已经批准的方案则进入待复核；不能只换显示文字。

超过单趟数量时，只有配置了明确的多趟规则才按趟次计算，否则标记为待确认。缺少线路或费用时不能补 0 元或由模型猜测。

### 6.2 三种结算方式的差异

| 结算方式 | 条件必填字段 | 对账户资金的影响 |
|---|---|---|
| 现金退款 | `refund_id`、`return_id`、`approved_refund_amount`、`expected_paid_at`、`actual_paid_at`、`cash_event_id`、`matched_amount`、`remaining_amount` | 银行／支付流水确认后才计实际现金流入 |
| 换货 | `exchange_id`、`return_id`、`replacement_sku_id`、`replacement_lot_id`、`replacement_qty`、`replacement_unit_cost`、`difference_amount`、`difference_direction`、`expected_arrival_at`、`receipt_ref` | 一般体现库存变化；仅差价的真实收付影响现金，不能把退回货值算成回款 |
| 抵扣货款 | `credit_note_id`、`return_id`、`credit_amount`、`issued_at`、`expires_at`、`applicable_supplier_id`、`payable_id`、`applied_amount`、`applied_at`、`remaining_credit` | 信用单签发本身不增加现金；应用于应付款后影响后续付款金额 |

还需 `payables.csv`：`payable_id`、`supplier_id`、`po_id`、`original_amount`、`due_at`、`paid_amount`、`applied_credit_amount`、`outstanding_amount`、`status`。付款、信用单核销分别用明细关联，避免汇总字段互相覆盖。

例：退回成本 1,000 元的货，供应商只愿退款 900 元，另发生运费 30 元，实际现金效果是到账 900 元、付出 30 元。不能按库存成本写“已回款 1,000 元”。若同样的 900 元是抵款，应先显示“获得抵扣额度 900 元”，核销时再体现预计少付；不得再加一笔 900 元现金收入。

### 6.3 不接供应商系统，也可以建立退供记录

**用户已确认此方案。** 统一流程为：**上传材料 → AI 提取关键信息并显示原文依据 → 采购或财务人员确认 → 关联退供任务 → 补充执行及结算凭据。**

黑客松版使用同一案例下的合成供应商协议、原采购单、沟通记录、退货验收单和结算凭据。选择一条结算主线完整展示；另外两种方式以独立分支保留，不能把同一批货重复计为退款、换货和抵款。

材料按回放时间逐步出现：协议只证明条款，后续供应商回复才证明本次接受，最后结算凭据才支持相应结算结果。模型提取遇到数量、期限或结算方式缺失时请求补充，不从后续回放答案中填值。

| 所需信息 | 最初可从哪里取得 | 首版如何进入系统 |
|---|---|---|
| 是否允许退供、期限及扣费 | 采购合同、供应商协议、已确认的往来文件 | 上传文件／人工录入，保留原文位置，业务人员确认结构化条款 |
| 这批货从谁采购、数量和价格 | 采购表、送货单、入库单、发票或对账单 | 文件导入并关联 SKU、批次与供应商；证据不足时待核查 |
| 本次供应商是否同意 | 微信文字／截图、邮件、采购员的电话确认记录 | 附原始材料或确认摘要，记录确认人、时间、数量和结算方式 |
| 退回多少、验收多少 | 退货出库单、承运单、供应商签收或验收单 | 上传回执或手工确认数量 |
| 退款到账 | 银行／支付平台导出流水、财务收款记录 | 导入流水后核销；仅有“同意退款”的聊天不能算已到账 |
| 换货完成 | 替换商品送货单与入库记录 | 关联换入 SKU、数量、批次和差价 |
| 抵款完成 | 供应商信用单、双方对账单、企业应付账款表 | 关联指定应付单及实际核销金额；没有应付单时仅登记未使用额度 |

真实试点可按条件逐步对接企业 ERP／进销存、仓储和财务系统。首版不要求供应商另建账号，也不要求先打通供应商系统；由企业采购或财务人员登记和确认既有证据即可。

AI 文档提取属于计划能力。提取结果保留原文依据，不能把“供应商可能同意”识别为“供应商已确认”，也不能以模型推断代替对方承诺。

## 7. 组合促销、阶段价格和销量预测怎么补

### 7.1 先建立可执行规则

| 数据集 | 必需字段 |
|---|---|
| 活动 `promotions.json` | `promotion_id`、`name`、`type`、`store_scope[]`、`start_at`、`end_at`、`budget`、`stacking_rule`、`approval_status`、`approved_by`、`version` |
| 阶段价 `promotion_stages.csv` | `stage_id`、`promotion_id`、`sku_id/bundle_id`、`start_at`、`end_at`、`selling_price`、`quantity_limit`、`stop_condition` |
| 组合组成 `bundle_components.csv` | `bundle_id`、`component_sku_id`、`qty_per_bundle`、`allowed_lot_ids`、`revenue_allocation_rule` |
| 价格约束 `price_policies.csv` | `policy_id`、`sku/category_scope`、`floor_price`、`min_gross_margin_pct`、`max_discount_pct`、`loss_clearance_allowed`、`exception_approval_ref`、`valid_from/to` |
| 活动成本 `promotion_costs.csv` | `cost_id`、`promotion_id`、`fixed_cost`、`variable_cost_per_sale`、`subsidy_amount`、`subsidy_confirmation_status`、`payment_date` |
| 需求假设 `price_response_assumptions.json` | `assumption_id`、`store_id`、`sku_id/bundle_id`、`reference_price`、`candidate_price`、`period`、`demand_low/base/high`、`method`、`evidence_ids[]`、`owner`、`created_at` |

确定性校验至少包括：

- 阶段时间不能冲突；活动不能超过该批商品可售期限；活动结束后不继续套用促销价。
- 组合售出 1 套，必须按组成同时扣减各 SKU 与批次；赠品也有成本。
- 组合可卖套数受最少的那个组成商品约束，不得超卖或忽略原本正常销售的消耗。
- 按统一价格口径检查底价与毛利。单品示例：最低售价 = 单位成本 ÷（1 − 最低毛利率），结果向上取到分；另与人工底价取更严格者。
- 组合以全部组成成本计算整体毛利，并保留收入分摊规则，避免把全部收入都归到滞销商品。
- 允许亏损清货时必须使用明确的例外授权和损失上限，不自动绕过约束。
- 预测销量、实际售出、实际到账是三个阶段；生成促销方案不等于已卖出。

### 7.2 分三个层次实施销量估计

**第一层：当前可做的情景试算。**

由业务人员给出保守、基准、乐观三个销量假设，或采用明确标记的合成价格响应曲线。分别计算各价格下现金、毛利、费用与剩余量。页面写“按假设估计”，三个场景不是统计置信区间。数据不足时允许只展示价格约束与盈亏平衡销量，不硬给销量结论。

**第二层：积累同店同商品、相似商品的活动记录。**

记录正常价、实际成交价、促销起止、陈列、可售库存、上架时长、交易数量、节假日和相关商品销量。不能把缺货导致的销量下降当成低需求，也不能把节庆增长全归因于降价。

**第三层：有足够数据后估计价格响应。**

使用可审查的统计／预测方法估计需求，按时间留出数据评价误差和不确定性；样本不足时降级到品类参数或人工假设。历史打折往往发生在商品本来就卖不动的时候，观察到的相关关系不直接等于降价效果；必要时用小范围对照活动积累证据。

Oracle 的零售优惠优化文档将历史需求建模、约束下的价格方案计算及执行反馈作为相连环节；其预测文档也讨论缺货、异常值等数据处理。这支持上述分步方案，但不代表本项目已实现这些能力，也不意味着固定长度的历史即可得到可靠模型。[优惠优化说明](https://docs.oracle.com/cd/F17841_01/orscs/pdf/191004/html/implementation_guide/offer-opt.htm)、[需求预测方法](https://docs.oracle.com/en/industries/retail/ai-foundation-cloud-service/25.1.201.0/aifug/forecasting-method.htm)。

Agent 负责收集缺项、选择可用方法、调用计算、解释差异及根据新事实重算。销量、毛利和约束结果由对应工具产生，不能让语言模型自行编造“降价 10% 必定多卖 30%”。

## 8. 不接采购系统时，如何完成采购前检查

### 8.1 首版人工衔接流程

```text
采购员上传拟采购单
  → 解析并暂存明细
  → 核对单位、门店、供应商与库存时点
  → 用户确认并发布数据版本
  → 检查现货、在途、需求、效期和付款计划
  → 生成建议下单量、差异说明与风险
  → 负责人确认方案
  → 导出建议采购单／采购消息，由采购员沿用微信、电话、邮件或原系统下单
  → 回填实际订单确认、单号（如有）和数量
  → 导入到货、付款结果并核对差异
```

可以先做“一次导入库存与在途、每次上传拟采购单、事后回填执行”的轻量操作。库存或在途过期时，提示更新并暂缓给出确定结论。

系统可以阻止**本系统内**未通过检查的草稿转为“建议已批准”，可以在导出报告中明确风险；未接外部系统时，不能阻止采购员在外部系统直接下单，也不能承诺检查了未上传的订单。

### 8.2 拟采购单和付款需要的字段

| 数据对象 | 必需字段 |
|---|---|
| 拟采购单头 | `draft_order_id`、`buyer_id`、`supplier_id`、`created_at`、`requested_delivery_at`、`status`、`data_version` |
| 拟采购单行 | `draft_line_id`、`store_id`、`sku_id`、`requested_qty`、`purchase_unit`、`unit_conversion`、`unit_price`、`minimum_order_qty`、`order_multiple`、`expected_expiry_date` |
| 采购约束 | `lead_time_days`、`review_period_days`、`cancellation_allowed`、`cancellation_deadline`、`cancellation_fee`、`change_confirmation_required` |
| 已确认订单 | `po_id`、`po_line_id`、`ordered_qty`、`canceled_qty`、`shipped_qty`、`received_qty`、`expected_arrival_at`、`supplier_confirmation_ref`、`status` |
| 付款计划 | `payment_schedule_id`、`po_id`、`payable_id`、`due_at`、`scheduled_amount`、`paid_amount`、`confirmation_status`、`cash_event_ids[]` |
| 检查结果 | `check_id`、`draft_line_id`、`original_qty`、`recommended_qty`、`reason_codes[]`、`projected_stock_by_day[]`、`payment_change_by_date[]`、`constraint_results[]`、`valid_until` |
| 外部执行回填 | `external_order_ref`、`draft_order_id`、`actual_ordered_qty`、`actual_unit_price`、`confirmed_at`、`evidence_ref`、`difference_reason` |

检查至少包含：

1. 在售需求与预计到货时间能否匹配，未来某天是否缺货。
2. 同商品现货、已确认未发货订单与已发货在途是否重复计数。
3. 是否有其他门店可调拨库存，以及调拨后是否确实可以减少外购。
4. 预计库存是否超过需求、容量或效期可消化数量。
5. 最小起订量、整箱倍数、供应商变更费用是否满足。
6. 同周期内已确认付款和拟新增付款是否超过已知资金安排；缺少其他经营收支时，只说明采购付款压力。

采购单头数量不能再与在途总量直接相加。未发货量 = 有效订购量 − 已发货量；未收货在途量 = 已发货量 − 已收货量。延期到货和延期付款分别记录，不能假定到货延后就一定晚付钱。

### 8.3 微信、电话、邮件和不可接入系统的采购怎么获取

采购检查需要取得拟采购内容与已知库存等数据；数据可以通过业务人员导入，不以采购系统 API 为前提。

| 现有采购方式 | 获取方式（计划实现） | 需要人工确认的重点 |
|---|---|---|
| 微信文字／图片 | 粘贴拟发消息、上传已有报价或订货截图；提取拟采购草稿 | 是询价、意向还是已确认订单；商品规格、箱袋换算、数量、价格、交货与付款时间 |
| 电话 | 通话前说／填采购意向；通话后补一条结果摘要，无需强制录音 | 对方是否确认、实际数量与约定日期；口头信息由采购员明确确认 |
| 邮件 | 粘贴正文或上传邮件及附件；有条件时再接授权邮箱 | 报价、订单、变更、取消的先后关系，不能将多封邮件重复算成多张订单 |
| 现有系统无 API | 导出 Excel／CSV；不能导出时人工录入或上传可读单据 | 数据截至时间、导出范围、未交货订单是否齐全、导入是否重复 |

统一接入流程：**原始材料 → 提取草稿 → 匹配商品与单位 → 用户确认 → 去重并发布事实 → 计算建议。**

首版不假设系统已自动读取个人微信或电话。自动收取消息需要另行确认对应平台能力、企业授权和实现条件；用户提供的文字、图片、文件可作为首版入口。图片识别和结构化提取仍需开发，现有导入接口不会自动完成这些步骤。

最低需要四组数据：

1. 门店商品现有库存及截至时间；历史销量／已确认需求假设。
2. 已订未到明细，至少有供应商、商品、数量、预计到货时间及订单状态；尚无外部单号时先分配内部编号。
3. 这次拟采购的门店、商品、规格单位、数量、报价、预计到货时间；现金试算另需付款约定。
4. 已知付款计划与账户数据，用于评估采购资金压力；缺失时只做库存数量检查，不声称已评估整体资金充足性。

新增 `procurement_intakes.json`：`intake_id`、`channel`、`source_ref`、`source_document_id`、`source_timestamp`、`message_intent`、`supplier_id`、`extracted_lines[]`、`missing_fields[]`、`confirmation_status`、`confirmed_by`、`confirmed_at`、`linked_order_id`、`supersedes_intake_id`、`data_as_of_at`。每个提取字段保留原文位置；不明确的规格、金额、数量或日期应请求确认。

让采购员只确认异常或不明确字段，供应商和常购商品匹配关系确认后复用。检查后的草稿直接生成可复制的订货文字／订单文件，减少重新抄录；发送仍由用户控制。

必须区分三个介入时点：

- **订货前拿到意向**：可以建议减量、替代调拨、延后采购。
- **订货后拿到确认**：只能评估是否有条件变更或取消，计入供应商条款和费用。
- **到货／付款后才拿到数据**：只能做库存处置和后续补货建议，不能回称“本次采购已被提前拦截”。

如果客户不愿下单前提供信息，也没有其他可用数据通道，应将能力描述为“定期采购建议／订单复核”，不能承诺所有采购都经过前置检查。对于缺少已订未到数据的情况，标出覆盖不足，避免给出确定的“需要补货”或“已节省金额”。

### 8.4 黑客松版采购入口：文字与单张清晰截图识别已确认

已确认首版文字主线：**“发给供应商前，先检查一下”**，一个入口承接不同渠道内容。微信内容可以粘贴，邮件正文可以粘贴，电话采购可以写一条意向摘要；已确认支持单张清晰截图识别＋人工确认，本轮不做 PDF 直接解析；PDF 可截取关键页或复制文字，具体见比赛版草案第 10.1 节。

#### 最小必做流程

1. **输入采购意向**：粘贴待发送的文字、上传一张清晰截图，或加载一份明确标记的演示原始材料；允许现场修改商品、数量、交期。
2. **AI 提取并核查缺项**：返回门店、商品规格、供应商、数量、单位、单价、到货及付款日期，并标出原文依据。识别“询价／拟采购／已确认订单”，不能混用状态。
3. **人工确认草稿**：确认商品匹配、箱袋换算和相对日期；不明确的字段保持待补充。提取成功不能自动变成已下单事实。
4. **调用检查工具**：读取同一版本的现货、已订未到、逐日需求与规则，计算建议数量、缺货情况和预计付款差额。
5. **老板确认建议**：展示原计划和调整方案的数量、金额与依据；确认只产生建议执行任务，不冒充供应商已接单。
6. **生成订货内容**：提供可复制的订货文字及可下载单据，供采购员沿用原渠道发送。比赛已确认用前端演示飞书通知和邮箱草稿，具体与本采购场景的衔接按比赛版设计草案第 7.2 节实施建议安排；真实渠道接入留待后续。
7. **回填结果**：录入供应商实际确认的数量和日期；比赛用逐步加载的演示回执体现已下单、到货、付款，均保留演示标记。

AI 环节必须对当次输入实际提取并处理缺项；数量、资金结果由工具实时计算。样例按钮只能填入原始材料，不能直接填“正确建议”。模型不可用时显示提取失败，允许手工完成字段录入；手工模式不标记成 AI 已分析。

#### 主线可使用的具体样例

输入原文：

> 给西湖古荡店订海盐薯片分享装 80g×8，100 件，40 元／件，10 月 5 日到货，10 月 16 日付款，供应商是零食优供。这条消息还没发给供应商。

该独立采购场景固定使用 2026-10-03 的数据版本，评估到 2026-10-16，共 14 天：

| 输入事实／规则 | 演示设定 |
|---|---|
| 当前库存 | 120 件，效期覆盖评估期 |
| 已确认在途 | 30 件，10 月 4 日到货，已付款；与订单关联后只计一次 |
| 未来需求 | 每天 10 件，14 天共 140 件，标记为演示需求假设 |
| 安全库存 | 70 件，按逐日库存检查 |
| 拟采购 | 100 件，单价 40 元，10 月 5 日到货，10 月 16 日付款 |
| 采购约束 | 最小量 10 件，按 10 件倍数下单；库存容量至少容纳原计划峰值；本场景不包含可用调拨替代 |

在上述假设下，需要补充的数量为 `140 + 70 - 120 - 30 = 60 件`，逐日检查无缺货且满足安全量后，建议从 100 件调整为 60 件。

- 原拟采购付款：`100 × 40 = 4,000 元`。
- 调整后拟采购付款：`60 × 40 = 2,400 元`。
- 同周期预计少支付：`1,600 元`，明确标为相对拟采购计划的预计变化。
- 原计划期末库存 110 件，调整后 70 件；这些结果均依赖需求、到货和付款假设。

该样例只定义待生成场景，不覆盖现有 SKU 的业务事实。生成时建立独立场景快照，关联其商品与单位，禁止把这些数字写死在计算结果中。

现场修改拟采购数量、需求或到货时间后，结果必须由工具重新计算；如果改成“供应商已经确认订单”，流程应转为订单变更条件核查。至少保留一条“薯片两箱，照旧”的不完整输入，让系统追问规格、每箱数量等关键缺项。

#### 必做与扩展范围

| 范围 | 内容 |
|---|---|
| 推荐必做 | 文字输入、实际模型提取、缺项确认、统一演示库存及在途、确定性检查、订货文字生成、回填跟进 |
| 已确认的截图识别 | 上传一张清晰订货截图；识别结果采用同一人工确认卡和检查工具，与退供材料共用识别流程；本轮不做 PDF 直接解析 |
| 已确认的渠道演示 | 前端模拟飞书采购任务、企微促销任务、邮箱草稿及回执；具体交互按比赛版设计草案第 7.2 节设计 |
| 后续真实渠道接入 | 实际创建授权邮箱草稿，或给指定飞书／企微负责人发送任务并接收回填 |
| 留待后续 | 自动读取微信聊天、电话录音转写、持续同步邮箱、采购系统自动写回、复杂格式附件批量解析 |

不完整输入、识别失败、重复导入、库存数据过期应有明确状态。电话意向先使用人工文字摘要；图片识别若未实现就保留为计划能力，不展示伪造的识别过程。

## 9. 执行、资金结果、核查与重算所需数据

审批后消息、邮箱草稿、任务回调及 Agent 分工的补充规范见 [Agent 分工与审批后执行架构](./AGENT_EXECUTION_ARCHITECTURE.md)。其中执行动作和渠道回执需纳入演示数据；渠道发送状态、业务执行状态、资金核销状态分别保存。

### 9.1 方案和执行

| 数据集 | 必需字段 |
|---|---|
| 方案 `proposals.json` | `proposal_id`、`version`、`data_version`、`policy_version`、`objective`、`horizon_end`、`baseline_id`、`assumption_ids[]`、`action_lines[]`、`status` |
| 行动行 `action_lines` | `action_line_id`、`action_type`、`store_id`、`target_store_id`、`sku_id`、`lot_id`、`allocated_qty`、`reservation_id`、`expected_cash_events[]` |
| 预留 `reservations.csv` | `reservation_id`、`proposal_id/version`、`store_id`、`sku_id`、`lot_id`、`qty`、`status`、`expires_at`、`released_at` |
| 审批事件 `approval_events.csv` | `approval_id`、`proposal_id/version`、`submitted_by`、`approver_id`、`decision`、`reason`、`decided_at` |
| 执行任务 `execution_tasks.json` | `task_id`、`proposal_id/version`、`action_line_id`、`assignee_id`、`due_at`、`status`、`planned_qty`、`completed_qty`、`failure_reason` |
| 出入库 `stock_movements.csv` | `movement_id`、`business_ref`、`store/location_id`、`sku_id`、`lot_id`、`movement_type`、`qty`、`occurred_at`、`related_movement_id`、`receipt_ref`、`action_line_id` |
| 实际销售 `sales_lines.csv` | `sale_line_id`、`sale_id`、`store_id`、`sku_id`、`lot_id`、`lot_attribution_method`、`qty`、`net_sales_amount`、`sold_cost`、`promotion_id`、`action_line_id`、`sold_at` |

人员主数据使用虚拟角色：采购员、店长、区域负责人、审批人。提交人、审批人和执行人分别记录；是否允许自审由显式规则决定，不能由“管理员”一个显示名称隐含所有角色。

任务应支持未开始、执行中、部分完成、已完成、失败、取消。审批通过后进入执行任务；商品销售完成、款项结算完成分别记录，不能审批一下就消失，也不能将任务完成当成到账。

库存守恒：期末 = 期初 + 采购入库 + 调入 + 可售退货 + 换货入库 − 销售出库 − 调出 − 退供 − 报损。出库、在途、收货三段通过业务单号关联；预留只占用可用量，不改变实物数量。

### 9.2 资金与匹配

| 数据集 | 必需字段 |
|---|---|
| 账户 `accounts.csv` | `account_id`、`currency`、`opening_at`、`opening_balance`、`restricted_amount`、`scope` |
| 实际现金流水 `cash_events.csv` | `cash_event_id`、`account_id`、`direction`、`amount`、`posted_at`、`counterparty_id`、`business_ref`、`payment_channel`、`source_receipt_ref`、`status` |
| 预计现金 `cash_forecasts.csv` | `forecast_event_id`、`proposal_id/version`、`direction`、`expected_amount`、`expected_at`、`basis`、`assumption_id`、`confirmation_status` |
| 核销关系 `cash_allocations.csv` | `allocation_id`、`cash_event_id`、`sale_line_id/return_id/payable_id`、`action_line_id`、`allocated_amount`、`matched_at`、`match_method` |
| 案例复盘 `case_results.json` | `case_id`、`proposal_id/version`、`risk_ids[]`、`execution_refs[]`、`sales_refs[]`、`cash_refs[]`、`baseline_id`、`period`、`result_status` |

一笔到账可以对应多个业务单据，但核销合计不得超过流水金额；一个单据也可以分次到账。未匹配金额显示“待核对”，不能猜测归属。退货冲正、支付手续费、部分退款必须有对应事件。

账户账面余额 = 期初余额 + 已记账流入 − 已记账流出。可用资金再扣受限金额。未来已确认采购付款单独展示，不提前从当前账户余额扣除；也不将未来销售额加进当前余额。

如果同一行动既提高售出又减少补货，现金改善按逐笔增量流入和流出计算，不再额外加上“释放库存成本”，避免重复计收益。

### 9.3 核查及变更场景

`investigation_evidence.json` 至少包含：`evidence_id`、`risk_id`、`source_type`、`raw_text`、`structured_fact`、`occurred_at`、`known_at`、`submitted_by`、`confirmation_status`、`confirmed_by`、`supersedes_evidence_id`。

至少准备一种影响决策的变更：接收店临时闭店、供应商拒绝现金退款、批次实际可用量减少、商品此前未上架。用户确认新事实后，受影响的旧方案应标记待复核，对未执行部分调整预留，重新调用计算并产生新版本；需要变更已批准的行动时，由老板确认。已完成部分保持原始记录。仅更新文字或版本号不算重算。

## 10. 必备代表性场景包

每个场景写清起始事实 ID、经营目标、允许动作、隐藏的后续事件、应出现的判断及不能出现的结果。场景文件不能直接告诉 Agent “正确答案是调拨”。

| 编号 | 场景 | 要展示的能力 | 必需结果／边界 |
|---|---|---|---|
| S01 | 坚果滞销，原店与接收店需求不同 | 调拨比较、审批、出入库、销售、到账 | 同一批货从风险到资金结果可追溯，见下方主线 |
| S02 | 坚果同时滞销与临期 | 两类风险独立识别，数量组合分配 | 风险金额不重复，分配数量不超库存 |
| S03 | 薯片临期但正常速度可售完 | 原店保留基线 | 不因临期标签强行调拨或降价 |
| S04 | 最畅销候选店已有大量现货与在途 | 校验接收店净需求 | 排除或减少调入，展示原因；更远的候选也可能不合算 |
| S05 | 供应商接受退货 | 退款、换货、抵款三个分支 | 三个独立回放分支互斥，不能同时退同一批货三次 |
| S06 | 饼干与饮料组合，分两阶段降价 | 底价、毛利、活动期限与组成扣减 | 拒绝违规价格；销量不足时给情景估计 |
| S07 | 采购员拟补货，已有库存与在途偏高 | 导入检查、建议减量、导出与回填 | 区分建议、实际下单、实际少付；不宣称拦截外部系统 |
| S08 | 店长反馈未上架或接收店闭店 | 核查、事实更新与重新计算 | 新方案数量／目的地／方式随证据变化 |
| S09 | 只调出一部分，销售尚未全结算 | 部分执行、部分到账 | 未完成和未到账继续保留，案例不提前记全部收益 |
| S10 | 正常商品与缺数据商品 | 不干预与请求补数据 | 不把所有商品都诊断为问题，不把缺数据当零 |

S04、S08、S09 可作为 S01 的分支，共用同一批商品。前端案例库只精选有代表性的 1—2 个／分类，其他分支用于演示切换或验收。

### 10.1 跨店调拨主线：一套能算清楚的数字

该主线与第 4.3 节的风险识别小样例为不同场景，不能将两者记录混在同一库存快照。

| 项目 | 主线设定 |
|---|---|
| 商品 | 每日坚果礼盒 750g，基础单位“盒”，成本 80 元／盒，售价 100 元／盒 |
| 调出店 | 西湖古荡店，主线批次库存 120 盒，近 30 天售出 12 盒 |
| 调入店 | 西湖文三店，同商品原有其他批次 10 盒，正常需求预测 4 盒／天，无已确认在途 |
| 条件 | 21 天评估期，运输 1 天；主线批次可售期限覆盖整个周期；容量、安全库存及其他候选按完整事实检查 |
| 方案 | 调拨 80 盒，运费 24 元；80 盒是该场景的可行候选，是否推荐须与其他方案一起计算 |
| 回放 | 调入 80 盒，21 天内其中售出 64 盒，剩余 16 盒；原店余下的 40 盒在此分支中尚未售出 |
| 收款 | 这 64 盒全部按 100 元成交并结算，到账 6,400 元；运费实际支付 24 元 |
| 成本 | 64 盒已售成本 5,120 元；企业该批库存从 9,600 元降至 4,480 元，因售出而减少 5,120 元 |
| 毛利 | 6,400 − 5,120 = 1,280 元；扣这笔运费后贡献 1,256 元，未扣其他经营费用 |

接收店原有 10 盒的销售独立记录，不能把它们归到这次调拨成果。需求预测和回放实际销量允许不同，差异需要保留。

案例应展示：发现依据 → 候选及排除原因 → 调拨方案与费用 → 审批人 → 调出与签收 → 批次售出 → 收款凭据 → 剩余库存。

上述数字全部为**演示回放**。6,400 元是这批商品的销售回款，不等于系统额外创造 6,400 元；1,256 元也不能直接称作系统增量利润。要计算系统增量效果，还需同周期“不采取行动”的基线，并明确基线是估算还是对照观察。

## 11. 当前缺数据的优先级与开发依赖

### P0：先让主线闭合

1. 统一商品／门店／批次／单位与快照版本，替代多处相互独立的演示数字。
2. 逐日销售、可售状态、效期和库存变动，支撑风险独立计算与解释。
3. 同 SKU 的候选门店现货、在途、需求、安全量和运输线路。
4. 同时点的原店保留基线及调拨候选，明确未确认数据和不确定性。
5. 审批、执行、签收、销售及资金流水之间的关联，完成一条 S01 回放。
6. 拟采购单及付款计划，支撑无 ERP 接入的检查流程。

### P1：补齐四种方式比较

1. 供应商条款、确认记录，以及退款／换货／抵款分支。
2. 组合促销、阶段价格、底价、毛利与费用规则。
3. 价格响应的三档情景假设及统一比较输出。
4. 组合行动的批次数量预留、失效释放和冲突处理。
5. 反馈导致的真实重算，以及部分完成、部分到账、退货冲正。

### P2：真实客户试点后增强

1. 用真实活动历史校准价格响应，积累预测误差及不确定性。
2. 接采购、库存和支付系统，减少重复上传和手工回填。
3. 真实权限、多人协作、供应商确认通道及更复杂结算。

代码需配套完成：新数据加载与快照发布、旧 API 字段适配、候选门店读取改造、四类计算工具、真实重算、执行及资金核销。数据包完整不等于这些能力已实现。

## 12. 验收标准与交接顺序

以下是后续验收需求，本次未执行。

### 12.1 数据验收

- 同样的种子、配置、生成器版本产生相同主键和金额结果。
- 所有商品、门店、批次、订单、方案、执行和收款引用均能找到上游记录。
- 每个库存行单位明确；日库存与变动守恒，无负库存；在途不双算。
- 四种基本风险组合符合规则，风险并集金额去重；无数据时返回缺项。
- 库存和销量都与选中的 SKU 对应，不套用统一门店参数。
- 当前可见事实的 `known_at` 不晚于回放时钟；未来执行与答案不得提前泄露。
- 正常售出、促销售出、调拨、退供分配数量不重复；多方案共享库存时有预留检查。
- 退供数量、验收数量、退款数量／金额可部分完成，差额有状态和原因。
- 换货不自动生成现金退款；抵款不同时记现金流入及少付支出。
- 每笔资金核销不超流水金额，账户余额能按流水复算；销售收入和到账允许不同日期。
- 原计划、变更计划、实际执行分开保存；延期付款不会显示成永久节约。
- 案例所有关键数量和金额能追溯到业务记录；同一事件不跨案例重复累计收益。
- 首页门店范围、地图评估范围、数据覆盖范围与实际记录一致。

最终交付应让使用者在一条案例中看清：**为什么处理、选了什么方案、实际做了多少、货还剩多少、钱何时到账、哪些结果仍是估算。**
