# snack-demo-v1 合成零食数据包

本包遵循魏的 [v0.3 API 契约](../docs/API_CONTRACT.md)，只提供合成输入和独立验收参考。`data_version=snack-demo-v1`、`policy_version=snack-policy-v1`、随机种子 `20261002`、分析日期 `2026-10-02` 均固定。所有金额均为人民币整数分，数量单位取商品的 `unit`。它不是客户数据，参考结果不是模型输出或真实收益。

```powershell
python sample-data/generate.py
python sample-data/generate.py --check
python -m unittest tests.test_sample_data -v
```

生成器仅使用 Python 标准库，不连接后端、数据库、网络或模型。重新生成会恢复同一份合成输入；`--check` 检查生成文件与当前定义逐字节一致，缺失或差异返回非零退出码。`--output <目录>` 可写到临时目录，清单写入该目录的父目录。版本控制强制清单与生成文件使用 LF，避免 Windows 换行转换改变 SHA-256。

## 输入、验收参考和测试响应

| 文件 | 用途 |
| --- | --- |
| `fixture-definitions.json` | 门店、商品、快照、逐日销量分布、采购、批次、规则及时间约定的输入定义 |
| `generated/dataset.json` | 元数据、假设与七个共享模型组成的完整 JSON 输入包 |
| `generated/{模型名}.csv` | 与 JSON 对应的七张表；日期、预留数量、在途数量和金额字段均保留；未知值导出为空单元格 |
| `generated/scenario_requests.json` | 五个固定 Agent 请求，现金场景同时提供预览与确认模拟请求 |
| `manifest.json` | 契约／数据／规则版本、日期、合成标记、scope 选项、场景目录、文件路径及 SHA-256 |
| `reference/scenario-requests.json` | 固定请求的源文件，符合 v0.3 的 `user_input/scope/params` 结构 |
| `reference/expected-results.json` | 独立维护的五个黄金场景参考数值与限定条件，不由生成器或业务工具计算 |
| `reference/data-quality-cases.json` | 9 个相互隔离的单门店商品数据集，包括正常对照与故意异常输入；各自使用独立数据版本 |
| `feedback-evaluation.json` | 24 条中文反馈、v0.3 请求及人工参考标注，真实模型评估尚未运行 |
| `../tests/fixtures/v03/response-*.json` | 六种状态与五 Agent 的浏览器契约测试夹具，不能作为运行时响应来源 |

清单只包含输入文件，不分发参考结果、异常数据集或响应夹具。前端可用 `scope_options` 显示合成门店、商品和品类选项，并提交真实 API 请求；接口不可用必须显示错误，不能把参考结果当作成功响应。v0.3 尚未定义数据导入、数据元信息或重置接口；运行生成器和下载数据不会将后端数据集安装或重置为本包，需魏在服务端加载并核对版本。

固定请求 ID、会话 ID、情景 ID 和假设只用于隔离测试参考，不能直接重放成一次已获确认的真实联调请求。真实联调每次运行都生成新的 `request_id` UUID；现金场景必须先发送 `operation=preview`，由用户核对本次返回的情景后，再复用该会话的 `session_id` 及本次返回的 `scenario_id`、`store_ids`、`horizon_days`、`adjustments` 和 `assumptions` 发送 `simulate/confirmed=true`。不要把文件中的固定情景或假设替换进服务刚返回的预览；示例 simulate 请求不意味着可以绕过预览与确认。

## 数据规模与口径

| 共享模型 | 记录数 | 内容 |
| --- | ---: | --- |
| `stores` | 3 | 滨江店、文二路店、城西店 |
| `skus` | 4 | 椒盐海苔脆片、每日坚果组合、草莓牛奶、香辣豆干 |
| `inventory_snapshots` | 5 | 五个门店商品组合；显式保留 `reserved_qty` 和 `in_transit_qty` |
| `sales_daily` | 76 | 五组各 14 天，共 70 条；另加滨江坚果 9 月 13—18 日的 6 条历史证据 |
| `purchase_orders` | 1 | 城西坚果 `PO-003`，未收货 30 袋 |
| `inventory_lots` | 1 | 文二路香辣豆干 `LOT-004-01`，40 袋，10 月 18 日到期 |
| `policies` | 3 | 脆片、坚果、豆制品的品类规则 |

- 销量窗口为 9 月 19 日至 10 月 2 日，含首尾，每天都有记录。五组总销量依次为滨江脆片 28、文二脆片 56、滨江坚果 0、文二豆干 14、城西坚果 28 袋。种子只打乱已声明的每日输入分布，不生成 Agent 计算答案。
- 库存取 `2026-10-02T23:59:59+08:00` 收盘快照，与当日完整销量保持同一截止时点；契约里的 08:00 是代表性示例。本包不声称存在盘中流水。
- 滨江坚果最近一次正销量为 9 月 13 日，此后到 10 月 2 日逐日明确为零，因此有完整的 19 天证据。零销量保留 `0`，缺记录代表未知；覆盖天数参考为 `null`，不使用 `9999`。
- 快照在途 30 袋与 `PO-003.open_qty=30` 是同一批货物的汇总和明细，不能叠加成 60 袋。现货、预留、在途分别保留。
- 只有香辣豆干提供批次，批次总量等于对应现货 40 袋。其他商品不编造效期；草莓牛奶仅有主数据，没有声明库存或销售，不能当作零值记录。
- 本演示从 10 月 3 日预测，约定到期日为最后可售日，10 月 3—18 日共 16 天。该约定需魏确认工具采用相同口径。真实业务仍需按门店可售截止规则判断。
- 采购按契约黄金场景保留“3 天销量扣减 6 袋、到货前约 4 袋”。到货与销售的日内顺序、逐日资金指标计量时点尚需冻结，不编造 30 天资金曲线或具体缺货日期。到货前 4 袋低于 5 天安全库存；没有后续补货计划时，基线和减量方案在 30 天内均有缺货风险。
- 本调拨场景允许按袋调拨，不能把采购箱规 24 袋强加为调拨整箱限制。采购坚果按 6 袋箱规调整。

五条独立黄金参考是：滞销坚果库存成本 22,000 分／超额 17 袋；脆片调拨 50 袋并展示两店前后覆盖；临期豆干风险估算 24 袋／6,480 分；采购量由 30 袋减至 24 袋；预计采购承诺由 26,400 分降至 21,120 分，减少 5,280 分。内部调拨不改变连锁总库存成本，采购承诺减少不等于银行余额增加。这些是验收参考，不能替代魏的工具实现与服务端测试。

## 独立异常输入

`reference/data-quality-cases.json` 包含正常库存对照、明确零销量、缺成本、缺经营规则、缺日记录、未知商品、预留超过实物、缺效期、批次数量与快照不一致。每条有独立 `input_dataset`、请求和应识别的问题；异常数据不混入 `snack-demo-v1`，不加入生成清单。正常对照的库存和销量仅用于该独立测试，不覆盖五个黄金场景。

`reference` 说明预期识别的问题及人工复核要求，不是已经执行的响应。需要后端测试加载该输入后再核对实际告警、缺字段与失败状态。此处的 Python 测试检查数据结构、异常确实存在和有效数据未被污染，不复制业务判定或计算服务。

## 中文反馈评测

24 条反馈覆盖商品／门店名称、别名与未知 ID、多实体、绝对与相对日期、非法日期、库存／销量／规格／计划量、包装换算、价格与运费、零销量与未知销量、否定表达、库存矛盾、冲突约束、退供条款、条件性采购及越权嵌入指令。

每条 `input` 是 v0.3 Agent 请求，`scope.as_of` 统一为 `2026-10-02`，时区为 `Asia/Shanghai`；相对时间按此固定锚点解释，“昨天”为 10 月 1 日，“明天”为 10 月 3 日，“上个月”为 9 月整月，“这个月”为 10 月 1 日至分析日。周定义、统计窗口是否包含当天等原文未明确的口径仍标为歧义。反馈是独立的语言评测案例，可与黄金库存不同，不会更新有效数据集。

`reference` 是待业务人员复核的人工标注，并非新增后端响应契约：

- 商品、门店、日期和数量的 `text` 必须是原文片段；明确名称可引用本包主数据 ID，别名保持未确认，未知编码保留为待核验候选。编码出现不代表主数据已验证通过。
- 数量另标 `unit` 和 `role`：`bag`、`bottle`、`box`、`day` 等不能直接混加。`bag/box` 和 `g/bag` 仅表示原文包装规格；模型不得自行换算出库存总量。金额用 `fen` 或 `fen/bag`，例如原文 8.80 元标为 880 分，保留原文证据。
- 明确的零值保留 `0`；未知数量为 `null`，非法或含糊日期不补造。合法约束保留原文，矛盾和歧义单独标注。越权指令保留为不可信原文，不视为合法业务约束。
- 所有条目都需人工复核，理由明确；“需要复核”不等于“模型字段一定错误”。模型负责结构化与解释，金额汇总、安全库存、可售期限及方案可行性仍由后端工具计算。

真实 AI 接入后，先复核并冻结参考标注，再记录相同模型、Prompt 与契约版本的完整评测。结果另存，保留请求编号、模型名称、原始输出、结构化输出、校验错误、耗时和人工修改项；不要覆盖原始语料或把确定性测试当作模型评分。

| 指标 | 建议统计口径 | 当前状态 |
| --- | --- | --- |
| 字段提取准确率 | 分别比较实体、日期、数量／单位／角色和约束，报告漏提取与多提取，未知不能按零值命中 | 未测 |
| 人工修改率 | 需修改结构化字段的反馈数 ÷ 有效模型输出数 | 未测 |
| 完整条目通过率 | 关键字段正确、缺项与冲突保留、没有生成未经确认事实的条目数 ÷ 总条目数 | 未测 |
| Schema 有效率 | 通过服务端 Schema 校验的响应数 ÷ 总请求数 | 未测 |
| 失败与恢复 | 单列超时、限流、非法 JSON、重试和人工接管，不排除失败后仅报告成功样本 | 未测 |

`evaluation_status` 保持 `not_run`，`model` 和 `metrics` 均为 `null`。本地测试只验证输入与参考资料，不声称真实 AI、后端计算、接口联调或业务执行已经通过。
