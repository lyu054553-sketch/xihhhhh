# 货不压钱｜比赛示例数据包

版本：retail-v2.1 · 生成于 2026-10-04  
决策时钟固定为 **2026-10-03 09:30（北京时间）**；不随电脑日期推进。

本包是用户要求生成的本地 XLSX 样例。应用在比赛演示模式启动时，现有场景加载器会把所选场景导入隔离的 `hackathon-demo` 事实库；原始 XLSX 不通过旧数据中心的库存上传入口重复导入。没有调用 ERP、支付、供应商或消息平台。数据、门店位置、材料及回执均为合成；渠道 UI 是否显示来源标签遵循比赛版设计草案。

## 1. 文件在哪里、先看哪份

| 03_需求路线采购与条款.xlsx | 2,160 条逐日需求假设、30 条路线、180 条日历、采购在途、账户、应付、退供条款和促销约束 | 事实与假设按工作表区分，不将预测当作实际销售 |

`manifest.json` 保存文件校验和、各表行数和字段列表；`data_dictionary.json` 保存字段类型与空值情况。`generator/build-data.mjs` 保存可重复生成的脚本，使用固定种子 `20261003`。XLSX 是这版样例的权威交付，07 是 02 的派生投影，不能把两份库存重复导入。

建议先打开 **06 的“金额复算”**了解主线数字，再看 **04 的“场景目录”**。正式计算查询只能读取被允许的原始字段。

## 2. 覆盖范围

- 完整门店：`ST-001` 西湖古荡、`ST-002` 西湖文三、`ST-003` 余杭未来、`ST-004` 上城庆春、`ST-005` 拱墅运河、`ST-006` 滨江长河。
- `ST-007`—`ST-050` 是名录占位，`include_in_summary=false`；不能显示已经接入 50 店或将缺数据填成零。
- 商品 `SKU-001`—`SKU-012`，包括坚果、薯片、饼干、糖果、果脯、饮料和肉脯。数量一律按商品 `base_unit`，不能把盒、件、箱混用。
- 90 天历史，每店每 SKU 每天都有销售和可售记录，包括营业有货但零销售；库存变动与期初、补货、销量、期末关联。
- 未来需求和收货日历覆盖 2026-10-03—11-01。回放在此窗口内提供代表事件，**不是 6 店未来 30 天的全部背景交易**。
- S01 调拨、S05 退款、S06 促销、S07 采购有主要业务与现金事件；换货、抵款是互斥分支；S08 为核查与重算输入，重算答案应由应用当次产生。
- 当前新数据 ID 是独立命名空间，接入时须按确认的门店／商品映射与旧样例关联，不能仅按同名覆盖数据库。

## 3. 金额、日期和来源

| 字段组 | 约定 |
|---|---|
| `*_id`、`*_ref` | 稳定字符串；按 ID 关联，不依赖商品文字 |
| `quantity`、`*_qty` | 基础单位数量；现货、在途、冻结和预留分开 |
| `*_amount`、`*_cost`、`*_price`、`*_fee` | 人民币元；金额保留两位；单价按基础单位 |
| `*_pct`、`*_ratio` | 百分数 0—100，例如毛利下限 20 表示 20% |
| `date`、`*_date` 等纯日期 | Excel 日期单元格，显示 `yyyy-mm-dd`；加载器读取后规范化为同格式字符串 |
| `known_at`、`occurred_at` 等时间 | 带 `+08:00` 的 ISO 时间文本；逐条按可知时点筛选 |
| 空单元格 | 未知或不适用，结合字段与场景判断；不等于 0 |
| `sellable_until` | 首个不可销售日期，销售日期必须早于它 |
| `source`、`is_demo`、`data_version` | 合成来源、版本；沿事实与回放保留 |
| `scenario_id`、`branch_id` | 场景隔离键；不是要合并的全部业务数据 |
| `external_write` | 三渠道记录固定为 false，不表示外部平台已收到 |

历史采购的已付款是采购凭据字段；账户 858,900 元来自独立时点余额样例，本包不试图由 90 天采购反推完整历史银行账。未来背景采购应付见 03；案例回放净额只统计自身列出的事件，不能替代全企业现金预测。

运输坐标及路线是人工录入的示意参数，费用为固定单趟新增支出，适用于 `SKU-001`、最多 100 盒。超量、不同单位或混载需新规则；没有报价的商品不得套用 24 元或自动填 0。

## 4. 加载次序与时间隔离

比赛事实加载器现已实现，以下保留数据隔离和业务口径约定；旧文件导入入口仍只支持其自身声明的字段：

1. 读取 manifest，建立隔离数据集和 ID 映射，解析 01 主数据。
2. 读取 02 当前事实及 03 对应事实／假设。相同 `shipment_line_id` 的在途明细和库存快照是同一资产的两种描述，不能相加两遍。
3. 由场景选择器读取 04，仅将所选场景的原始输入和已确认覆盖项提供给工具。**场景标题、分支名、备注、验收预期用于运行夹具，不放入模型事实查询**；它们可能包含预设回放结果线索。
4. 查询事实还须满足 `known_at <= 当前场景时钟`；未来日期的预测可提前知道，未来实际签收或到账不可提前知道。
5. 应用实际生成方案，管理员一次确认后创建批准记录和任务。05 的预置任务仅用于重现指定回放，不代表实际 AI 已产生了方案。
6. 播放 05 时使用场景 + 分支 + 事件 ID 去重，并核对当前批准版本及数量。修改了方案就不能继续套用原来的 80 盒回放。销售表产生销售出库；业务回执产生调拨／采购／退供库存事件；不能把同一库存变动再重复登记。
7. 到账只能由现金流水产生，核销表仅说明资金分配。渠道“已发送”不产生销售、订单确认或现金。
8. 06 只能供开发验收读取，永远不挂在 Agent 工具的数据权限下。当前接口尚不支持整包自动加载；不要将 01—06 当作库存模板上传。

`known_at` 也是 04 场景批次的约束：例如采购新到货批次在 10 月 5 日之后才可加载。S08 闭店覆盖只能在相应反馈经确认后生效，不能在初次方案中偷看后续反馈。

## 5. 场景如何使用

| 场景 | 输入与操作 | 要看什么 |
|---|---|---|
| S01 | 古荡坚果原批 120 盒；文三原有另批 10 盒；当前日需求假设 4 盒；录入路线 24 元 | 80 盒候选经实际计算与确认后才允许播放该分支；到货后原批售 64，另批销售单列 |
| S02 | 独立风险输入：100 盒、近 30 天售 30、剩余可售 10 天 | 同时命中滞销、临期；该批成本只统计一次 |
| S03 | 原始快照：薯片 60 件、近 30 天售 300、剩余可售 10 天 | 临期仍可能正常清完，不能机械促销 |
| S04 | 未来店坚果现货 200、在途 100、日需求假设 8 | 先算净需求，销量高不等于应继续调入 |
| S05 | 独立退供快照 100 桶、成本 10 元；关联协议、原采购凭据、确认、验收 | 退款、换货、抵款三选一；不能三次处置同一批货 |
| S06 | 庆春店饼干 + 果汁各一件为一组；第一阶段 11 元、第二阶段 10 元；底价 10、毛利下限 20% | 组合最多 40 组，阶段共享库存；低中高需求是情景假设；正常销量不另加 |
| S07 | 独立采购起点：现货 120、已付在途 30；未来 14 天每天需求 10；期末安全量 70；意向 100 件 | 程序算需采购 60；原计划 4,000，调整 2,400；少付 1,600 是同周期计划差额 |
| S08 | “30 天仅上架 5 天”文字；或初次方案后确认文三闭店 | 前者需核查，后者重算；旧版本保留；不能写死新的推荐门店 |
| S09 | 同一初始状态的另一分支，计划 80 盒仅发收 60；售 40 而只到账 3,000 | 剩余 20 未执行、1,000 未到账；不能显示全部完成 |
| S10 | 正常、缺销量、缺效期等独立输入 | 未知保持空值；可判断的一种风险照常返回，另一种保持待补数据 |

### 独立快照的具体处理

- S02、S10 及 S08 的上架不足分支使用“独立风险输入”作为完整的风险只读输入，**不再拼接 BASE 的日销售补缺**；否则缺数据样例会被误补齐。
- S05 将选中门店商品替换为专用批次，专用采购材料作为期初来源。S07 以独立期初库存 120 为准。它们是新的场景快照，不能拿 BASE 的历史期末断言该快照已对账；原历史不覆盖。
- S05 抵款分支另有已确认应付 2,000 元，900 元额度使用后实际支付 1,100 元；换货回放换入 100 件、每件成本 9 元，差价 0。
- S07 在途 30 件只接收一次且已付，不再生成第二笔付款。回放按先到期先出消耗原有 120 件，再消耗已付在途中的 20 件；最终剩 10 + 60 = 70 件。
- S06 将组合价格分摊到明细：首阶段饼干 7 元、果汁 4 元，后阶段饼干 6 元、果汁 4 元；组成商品销售收入之和等于组合收款。不是训练出的价格弹性模型。
- S01 原批销售收款 6,400、成本 5,120、运费 24、扣运费贡献 1,256；目标店原有 10 盒的 1,000 元收入另记。贡献不等于增量利润，没有对照基线不能声称都由 Agent 创造。

## 6. 状态样例的使用范围

渠道动作的五个状态已经产品负责人确认。本包先提供保存草稿和已发送的代表记录；失败、重试等交互仍需开发。

执行 `pending / in_progress / completed` 与核算 `pending / in_progress / completed` 是**待产品负责人确认的简化设计**，不覆盖当前 API 状态枚举。S09 预期展示“执行中，60/80 盒；核算中，待到账 1,000 元”。异常明细仍保留；取消只作归档处理，不计入正常完成。

## 7. 下一步接入工作

1. 完成统一包加载器、ID 映射、场景快照、时间过滤与导入报告。
2. 把风险、候选店、方案比较和现金工具接到同一事实来源；实际 AI 只调这些工具。
3. 实现一次确认与任务创建的幂等、事务衔接，再连接三个本地渠道交互。
4. 接入部分回执、批次出入库与现金核销，最后用 06 对照结果。

本数据包的生成与应用加载属于不同阶段。现有代码在比赛演示模式启动时读取并保存场景事实；数据连接页通过只读接口展示入库状态与库存预览。应用联调与断网运行仍需单独验收。
